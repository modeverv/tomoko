1. なぜこの形にするか

v3 では日本語 Moshi 系を土台にしようとしたが、次の 2 点で行き詰まった。

  • 賢さが足りない。 Shizuku AI のブログの表でも、J-Moshi と LLM-jp-Moshi は QA 正答率が 1% 前後だった。
  • 外から文を与えても話せない。 v3 の実験で、学習なしのテキスト上書きは文として崩れた（v3/_docs/v0/moshi-text-forcing.md）。

Shizuku-Duplex と同じ作り（音声を直接聞いて直接話す一つのモデル）は、学習の規模が個人の範囲を超える。手本の SALM-Duplex は A100 を 32 枚、NemotronLabs VoiceChat は GPU を 64 枚使っている。費用の大半は、LLM に耳と口を覚えさせる部分にある。

一方、間合いの判断そのものは軽い。相づちと発話終了の見込みは MaAI が音声から直接出す。v2 が未完だったのは、次の 2 点である。

  • 材料の合成が手書きの式で、閾値と例外が増え続けた。
  • 通しの数字を外部の基準で測ったことがなく、実会話での検証前に終わった。

v4 はこの 2 点だけを直す。部品は既製品を使い、指揮者を小さく作り直し、採点を先に用意する。

3. 全体の構成

v4 は 2 つの独立したプログラムでできている。

  • 対話エンジン: /ws を 1 本だけ開くサーバー。マイクの音を受け、声を返す。
  • ベンチ: /ws につなぐクライアント。決まった入力音声を実時間で流し、返ってきた音を録って採点する。
ベンチはエンジンのコードを一切読み込まない。つながるのは /ws だけである。これにより、採点は「実際に聞こえた音」だけで行われ、エンジンの内部ログの都合に左右されない。ベンチを別のシステムの採点にも使える。

4. 対話エンジン

4.1 指揮者

指揮者は、会話の状態を持つ唯一の場所である。tick ごとに次の順で動く。

  1. センサーが書いた最新の材料を読む。
  2. 働き手から届いた結果を受け取る。世代が古いものは捨てる。
  3. 方針に材料と状態を渡し、行動を 1 つ受け取る。
  4. 行動を実行する。働き手を起こすか、取り消すか、何もしない。
  5. 材料、行動、理由をトレースに書く。
指揮者の中で LLM や TTS の完了を待たない。 v2 では、受信ループの中で LLM・DB・TTS を順番に待ったため、入力と割り込みが詰まった。v4 では、時間のかかる仕事はすべて別のタスクにし、指揮者は結果を受け取るだけにする。1 tick の処理は数 ms で終わる量に保つ。

4.2 行動

行動意味実行すること
WAIT黙って聞く何もしない
PREPARE声は出さずに、返事を作り始める途中経過の文字で手前の LLM を起こす
BACKCHANNEL相づちを打つ短い音声を話者に渡す。発言権は取らない
SPEAK話し始める、または続ける準備済みの文を話者に渡す
STOP話すのをやめる世代を進め、LLM と TTS を取り消し、再生を止める
DELEGATE裏に仕事を頼む裏の仕事を起こす。会話は続ける

PREPARE と SPEAK を分けるのが、無音待ちをなくす要点である。MaAI が「もうすぐ言い終わる」と出した時点で返事を作り始め、言い終わりが確かになった時点で声を出す。途中経過の文字が大きく変わったら、作りかけを捨てて作り直す。

4.3 世代

古い結果が後から届いて話してしまう事故を防ぐため、番号を 2 つ持つ。

  • 判断の世代: ユーザーが話し始めたとき、STOP したとき、途中経過の文字が大きく変わったときに進める。LLM と裏の仕事の結果には、起こしたときの世代を付ける。届いたときに世代が違えば捨てる。
  • 再生の世代: STOP のたびに進める。話者とクライアントは、古い世代の音を再生しない。

この 2 つを 1 つにまとめない。v2 の経験では、判断のやり直しと再生の停止は別の時刻に起きる。

4.4 方針

方針は「材料と状態を受け取り、行動と理由を返す」だけの関数である。状態を書き換えない。差し替え可能にする。

  • 最初の方針: 少数の明示的な規則で書く。閾値にはすべて名前を付け、判断のたびに使った値をトレースに残す。
  • 規則を足す条件: ベンチのどの項目が、どれだけ良くなるかを数字で示せるときだけ足す。v2 は cue と例外を足し続けて、会話の中心が 1,600 行級になった。
  • 後の方針: トレースとベンチの注釈が貯まったら、同じ入出力の小さな学習モデルに置き換えられる。これは学習の規模が小さく、手元の機材で足りる見込みである（未検証）。

4.5 材料

材料出どころ欠けたときの扱い
ユーザーが話しているか、無音の長さVAD必須。欠けたら WAIT
譲る見込みMaAI vap欠損は 0 として扱う。「観測できないから譲った」としない（v2 の決定）
相づちの頃合いMaAI bc_2type欠けたら相づちを打たない
途中経過の文字、前回からの変化量STT欠けたら PREPARE しない
自分が話しているか、どこまで話したか再生の追跡必須
裏の仕事の結果が届いているか文脈なければ何もしない

センサーが失敗しても会話を止めない。失敗は件数と一緒にトレースに残し、黙って消さない。

4.6 手前の LLM と裏の仕事

Shizuku-Duplex、GPT-Live、Thinking Machines の Interaction Models は、どれも「すぐ返せることは手前の小さいモデル、重いことは裏の大きいモデル」に分けている。v4 も同じ分け方にする。

手前の LLM裏の仕事
役割雑談、簡単な質問への答え、裏の結果を自分の言葉で伝えるWeb 検索、道具の呼び出し、時間のかかる推論
速さ最初の文字まで数百 ms数秒から数十秒
起こし方指揮者の PREPARE手前の LLM が出す依頼の印、または決定的な規則
結果の行き先文として話者へ文脈の末尾に <info> として追記

裏の結果の扱いは、決定的な側とモデルの側で分担する。

  • 決定的な側: 何を取りに行くか、期限、重複の除去、私的な情報を外に出さないこと、失敗の通知。
  • モデルの側: いつ言うか、どう言うか、言うかどうか。

結果は文脈の末尾に足すだけにする。途中を書き換えないので、LLM の計算済みの部分（KV キャッシュ）がそのまま使える。

4.7 話者と再生の追跡

TTS は差し替え可能な部品とし、次の 3 つを満たすものを使う。

  • 短い句の最初の音が速く出る。
  • 途中で取り消せる。
  • どこまで再生したかが分かる。

文は句の単位で TTS に渡す。STOP のあとに「実際に聞こえた範囲」を文脈に記録する。作った文の全体を、話した記録として残さない（v2 の教訓）。

4.8 文脈と圧縮

  • 原本: ユーザーの発話、Tomoko が実際に話した範囲、裏の結果を、追記だけで残す。
  • LLM に見せる文脈: 原本から作る。約 5 分ごとに古い部分を要約に置き換える。切り替えは、依頼と依頼の間に行う。
  • 記憶と人格: v1 の資産を、P6 以降で戻す。最初は入れない。

4.9 /ws の取り決め

向き種類中身
クライアントからサーバーバイナリマイクの音。16 kHz、モノラル、float32
クライアントからサーバーJSON再生の報告（どの世代を、どこまで再生したか）
サーバーからクライアントバイナリ声の断片。先頭に再生の世代と通し番号を付ける
サーバーからクライアントJSON停止（世代を指定）、文字の表示、状態の表示

クライアントは判断をしない。届いた音を順に再生し、停止が来たらその世代の音を捨てる。ブラウザとベンチは、同じ再生の規則を実装する。

5. ベンチ（採点の仕組み）

5.1 考え方

  • 時計はベンチが持つ。 入力の最初のサンプルを送った時刻を 0 とする。出力は、クライアントが再生するはずの時刻に置いて output.wav に録る。
  • 採点に使うのは、入力の注釈と output.wav だけ。 エンジンのトレースは原因調べに使い、採点には使わない。
  • 時刻は VAD で取る。 output.wav に VAD をかけ、Tomoko の発話区間を出す。書き起こしは中身の採点にだけ使う。
  • 答えなかった回を分母から外さない。 無音で終わった回は失敗として数える（v2 の教訓）。
  • 前提が成り立たなかった回を別に数える。 「Tomoko が話している最中に割り込む」項目で、Tomoko が話していなかった回は、成功にも失敗にも入れず、件数を報告する。

5.2 シナリオ

1 件のシナリオは、ユーザー側の台本と注釈でできている。

{
  "id": "interrupt-012",
  "axis": "T4",
  "steps": [
    {"say": "東京の観光地をいくつか教えて", "at": 1.0},
    {"say": "あ、ごめん、やっぱり大阪で", "after_tomoko_speaks": 2.0}
  ],
  "expect": {"topic": "大阪の観光地"}
}
  • at: 決まった時刻に流す。
  • after_tomoko_speaks: Tomoko の声を検出してから、指定の秒数後に流す。割り込みと相づちの項目で、前提を確実に成り立たせるために使う。

実際に流した時刻は、ベンチが実行ごとに記録する。採点はその記録を使う。

5.3 入力音声

種類作り方置き場所
合成台本を TTS で読ませる。話者を複数にする。言いよどみは無音の挿入で作る。生成スクリプトと台本を Git に入れる。音声は生成物なので入れない。
本人の録音ユーザーが台本を読む、または自由に話す。Git 管理外。クラウドに送らない。

合成だけでは、合成の声に合わせた調整になるおそれがある。関門の判定には、本人の録音での結果も併記する。

5.4 採点器の検査

採点器そのものが正しいかを、答えの分かっている偽のシステムで確かめる。

偽のシステム振る舞い期待する結果
無言何も返さない応答率 0、割り込み率 0、無音の回が全件
おしゃべり常に話し続ける言いよどみへの割り込み率 1、停止率 0
時計じかけ入力終了の 0.5 秒後に 2 秒話す遅れ 0.5 秒（誤差は VAD の刻み以内）

6. 評価軸

Full-Duplex-Bench の v1.0 と v1.5 の項目を参考に、日本語と一人用の使い方に合わせて定義し直した。コードは写さず、定義から書く。数値の窓はすべて仮で、P1 の中で確定する。

8. v1・v2 から引き継ぐ規則

リポジトリの AGENTS.md と _docs/knowlaedge.md から、v4 でも守るものを挙げる。

規則v4 での形
WebSocket は 1 本/ws だけ。ベンチも同じ口を使う。
クライアントに判断を置かない再生と停止の規則だけ。ブラウザとベンチで同じ。
推論の層は Web の枠組みに依存しないfront_llm.py と background/ は FastAPI を読み込まない。
状態を分散させない状態は指揮者だけが持つ。方針は関数。
層をまたぐときは型を通すdto.py に集める。VAD の内側だけは生の配列のまま。
音が出た、答えた、聞こえ終わった、を分けるトレースで別のイベントにする。T1 の遅れは本発話で測り、相づちは別に数える。
部品単体の速さを会話の速さとしない速さは必ずベンチの通しで報告する。
テストを先に書く採点器と方針は、実装の前に単体試験を書く。
私的な情報をクラウドに出さないクラウドに出せるのは、合成のシナリオとその結果だけ。本人の録音と実会話は出さない。

9. 未確認のこと

項目何が分かっていないか確かめる段階

追記 2026-11-13（Codex）: 5.3 入力音声の 1 回合成

5.3 の合成方法について、既定の「部品を別々に合成し、ゼロを挟む」方式に加え、 bench.generate --one-pass を選べるようにする。Step.parts() の無音の秒数を [[slnc ms]] に置き換え、1 発話を 1 回の say で合成する。 16 kHz、前後の無音除去、最大振幅 0.5、キャッシュの保存方法は共通にし、 1 回合成のキャッシュキーには one-pass| を付ける。既定の音声・注釈・キーは変えない。

1 回合成の voiced は振幅の絶対値が 0.005 を超える区間から作り、 0.15 秒未満のすき間をつなぐ。pauses は結合前の内部無音から長い順に台本の区切りの数だけ選び、 時刻順に戻す。先頭と末尾の無音は候補にしない。それぞれが要求長の 80% 未満、または候補不足なら、 台本 ID・発話番号・区切り番号を含む例外にする。検証は表示用の時刻の丸め前に行う。

句点や文字は取り除かないので、声が持つ自然な間は埋めた無音に加わる。 短い明示 pause の検出と voiced の平滑化は独立しており、0.15 秒未満の pause は結合した voiced の中に入りうる。 生成物には Manifest.one_pass を保存する。既定値は false とし、 この項目のない古い scenario.json も読める。単体試験では合成関数を差し替え、 say とモデルを呼ばずに検証する。

追記 2026-11-13（Codex）: 共有エンコーダーの MaAI センサー

engine/sensors/maai.py に MaaiSensor を追加した。 MaaiMultiple の共有 Mimi で vap / bc / bc_det を動かすための部品であり、 指揮者や基準線への接続は今回の作業に含まない。モデルは外から工場関数で渡し、 センサーの専用スレッドから同期の process(ch1, ch2) を呼ぶ。 MaAI 自身の入力 worker は起動しない。

ユーザーの16 kHzの音と、予定再生時刻を付けた Tomoko の24 kHzの声を、マイクの時計で 同じ範囲にそろえる。予測は engine/dto.py の MaaiFrame にする。 待機フレームを破棄したときは数とログを残し、入力時刻の欠落でモデルの文脈をリセットする。 実モデルの推論・精度・負荷は未検証。 API、チャンネルの向き、未着音声の補間と終了の規約は MaAI センサーの文書に記した。

追記 2026-11-13（Codex）: 言い終わりの CPC vap を分離

直前の追記の「基準線への接続を含まない」という範囲は、今回の接続追加には適用しない。 maai=True と maai_vap_cpc=True のときだけ、 相づちの Mimi（bc / bc_det、12.5 Hz、文脈20秒）とは別に、 CPC（vap、10 Hz、文脈5秒）を SharedMaai で起動する。 既定は False とし、従来のモデル構成を保つ。

接続ごとの2センサーはともに ch1=ユーザー、同じマイクの時計と予定音声を使う。 CompositeMaai は主の相づち予測と副の vap / vad を結合し、 鮮度判定には古い方のフレーム時刻を使う。片方が未出力ならある側だけを返す。 通知は両方とも session.on_maai に送り、判断処理と /ws の通信仕様は変えない。 vap だけを指定した場合は CPC センサーを直接つなぐ。実モデルの速度と精度は今回未測定。
