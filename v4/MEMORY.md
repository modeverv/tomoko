### 1 回合成の注釈の境界（実装中の気づき）
- 要求した無音の 80% をサンプル数に四捨五入すると、端数を持つ要求では 80% 未満を許してしまう。必要サンプル数は切り上げ、表示用の秒の丸めより前に判定する。浮動小数点の境界誤差だけは 1e-9 サンプルの許容を置く。
- voiced の短いすき間をつなぐ前の音量区間から pause 候補を取る。0.15 秒未満の pause も、voiced の結合とは別に検出できる。

### 確定した判断: 既定の入力を保つ追加方式

- 注釈の振幅閾値は 0.005、voiced の結合は 0.15 秒未満。pause は内部無音の長い順から選び、時刻順に戻して要求長と照合する。先頭・末尾の無音は選ばない。句点の自然な間を人為的に短くしない。

## 2026-11-13（Codex）: MaAI のオフライン評価

### 確認したことと評価器の判断
- vap / bc_det の公開入力は user,system。vap は Tomoko 側の p_now[1] / p_future[1]、bc_det はユーザー側の p_bc_det[0] を集計する。bc / bc_2type は内部で swap するので、公開入力は system,user とする。bc の p_bc_detect と bc_det の p_bc_det は別物。
- 無音も Chunk で渡して stereo を保つ。MaAI の Zero / ch2 省略は mono の選択に影響する。
- オフラインでは Maai.process() を同期で1フレームずつ呼び、その場で1結果を回収する。start() の起動時キュー消去と stop(wait=False) の競合を避ける。モデル・encoder・KV と結果キューはクリップごとにリセットする。
- 生成済み入力は各シナリオの最初（T3/T4 は最後も）を独立したクリップにし、前1秒・後2秒の無音を付ける。注釈の pauses と最後の voiced を使い、自然な TTS の小休止は別途検出しない。voiced は合成テキスト全体の注釈であり、連続した有声音の保証ではない。
- bc_det は最後の発話の voiced と終了後0.4秒で最大値を取り、1発話を1標本として AUC を計算する。長さによる最大値の偏りと、Tomoko 側無音という制約がある。同時発話での有効性はまだ確かめていない。
- 観測した最後のフレームを超える vap の遅れは欠測にする。実際のモデル variant も結果に残し、MC から標準モデルへのフォールバックを見分けられるようにする。
- 旧 run + vap の JSON は行リストを維持し、生成入力／複数モードは設定・計測・集計を含む schema_version=2 にした。使い方は _docs/maai-offline.md。

## 2026-11-13（Codex）: MaAI センサーの静的確認

- MaAI 0.2.27 の MaaiMultiple は、コンストラクタで runtime reset 済み。同期 process(ch1, ch2) を使うときに start() は不要。両側を Chunk にして mono の選択を避ける。終了時は process が戻った作業スレッドから stop(wait=True) を呼べる（指定された site-packages/maai/model.py:953-980,1113,1191-1211）。
- Mimi ONNX は最初の encoder 出力を意図的に捨て、空特徴でも出力しないことがある。同期 process の後に result_dict_queue が空でも無期限に待たない（model.py:1281-1295）。結果の時刻は壁時計 t ではなく、呼び出した入力フレームの終端サンプルから付ける。
- Multiple の辞書はトップの mode label の内側に各出力が入る。bc.p_bc と bc_det.p_bc_det は別の信号であり、bc.p_bc_detect を後者の代用にしない（model.py:1340-1406,1444-1495）。
- mimi_onnx_cpu_intra_threads / mimi_onnx_cpu_inter_threads は正式なコンストラクタ引数。torch のスレッド数だけでは ONNX の負荷は制限されない。今回は実モデルの読み込み・負荷測定を行わない。

### 確定した判断: センサー単体の入力・通知契約（Codex の実装）

- MaaiSensor は接続ごとのインスタンス。既定は1280サンプル、待機上限4フレーム、モデル入力 ch1=ユーザー。user_channel=1 で逆入力にし、DTO は常に (ユーザー, Tomoko) 順へ戻す。BC の意味として正しい向きは未確定で、ユーザーの判断や実測結果にしない。
- Tomoko の24 kHz のサンプル位置を保ってから、マイクのフレームへ線形補間する。すでに予約した声の後ろへ連結し、各断片の長さの丸めを累積させない。未着の隣接サンプルは待たず右端保持し、過去に推論へ渡した入力は再計算しない。
- 待機フレームを捨てた際は feed_mic の返り値と dropped_frames 累計と warning で観測する。入力時刻の欠落を検出したら encoder / KV をリセットし、欠けた音声の前後を連続した履歴にしない。
- close 後の未実行通知は配送時に抑止する。同期 process は強制停止できないため、close の期限超過は TimeoutError。モデルの一次エラーを終了処理の二次エラーで上書きせず、両方のログを残す。
- 25件の合成・偽モデル試験を追加し、全155件の unit と ruff が成功。独立 Codex（gpt-6.1-sol / max）の静的レビューを受け、指摘3点は先行の回帰テストで再現後に修正した。実モデルや相づちの体験品質を確認した結果ではない。

### MaAI で分かったこと（2026-11-13）
- bc（相づちの予測）は、ユーザーの声を ch1 に入れる。逆向きでは p_bc がほぼ 0。bc の日本語の重みは Mimi（12.5 Hz、文脈 20 秒）だけ。

## 2026-11-13（Codex）: CPC vap と Mimi の併用

### 確認したこと
- 単体 Maai の同期出力は、Multiple の mode 別ネストと違って `p_now` / `p_future` / `vad` をトップへ置く。既存 `_to_frame` へそのまま渡すと list に `.get()` して失敗する。先行の偽モデル試験で再現し、両形式に対応した。指定された MaAI 0.2.27 のコードも独立 Codex が静的確認した。
- `maai_modes="vap"` から vap を除くと空になる。空の Multiple は既存工場が拒否するため、この場合は Mimi を作らず CPC のセンサーだけをつなぐ。

### 確定した判断: 今回の実装契約
- ユーザー指定の `maai_vap_cpc=False` を追加。True かつ `maai=True` で、Mimi の modes から vap を除き、CPC vap（normal / 10 Hz / 5秒 / 1600サンプル）を別の SharedMaai にする。両工場の torch_threads は同じ設定値にする。False は従来の構成を保つ。
- `CompositeMaai` は主の bc / bc_det と副の vap / vad を合わせる。時刻は古い方、片方のフレームが欠けたらある側だけ、両方欠けたら None。個々の欠測を別モデルで補完しない。破棄数は合計、終了は両方を試して最初の例外を保持する。
- CPC 有効時のユーザー入力は両方 ch1、通知は両方 session.on_maai。baseline.py は変更しない。CPC の単体 factory は Chunk を2個使い、start() を呼ばない。
- これらはコードと偽モデル試験で確かめた実装の契約であり、実モデルの精度・CPU 負荷・会話遅延・体験品質を測った結果ではない。
