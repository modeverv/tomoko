1. 作業の規則

  • 最初に読むもの: この文書、ARCHITECTURE.html、リポジトリ直下の AGENTS.md、v4/MEMORY.md、v4/LOG.md の末尾。
  • 作業場所: 新しいものはすべて v4/ の中に置く。v1/、v2/、v3/ は読むだけにする。
  • この文書の直し方: 追記だけにする。既存の記述を変えるときは、末尾に新しい節を足して、どこを改めるかを書く。チェックの状態だけは書き換えてよい。
  • 記録: 作業の始めと終わりに v4/LOG.md へ書く。判断と気づきは v4/MEMORY.md へ書く。どちらも追記だけ。
  • テスト: 採点器と方針は、実装の前に単体試験を書く。テストが通る単位でコミットする。
  • コミット: 作者名を、作業したエージェントの名前にする。メッセージには理由を書く。git push --force は禁止。
  • シェル: コマンドの頭に rtk を付ける。
  • 共通記録: 決定、報告、問いは、Google Drive の llm に新しい org イベントとして保存する（ユーザーの全体指示）。
  • 私的な情報: 本人の録音と実会話の記録は、Git に入れず、クラウドに送らない。

2. 1 回の変更の回し方

P3 以降は、この手順を繰り返す。

  1. 仮説を書く。 「どの軸の、どの数字が、なぜ動くはずか」を LOG.md に 1〜2 行で書く。
  2. 変更は 1 か所。 2 つ同時に変えない。
  3. 小さい組で測る。 各軸 10 件ほどの組を回す。数分で終わる量にする。
  4. 前回と比べる。 bench/report.py が、前回との差を軸ごとに出す。
  5. 残すか戻すかを決める。 狙った数字が良くなり、ほかの軸が悪くなっていなければ残す。それ以外は戻し、結果だけを記録に残す。
  6. 節目で全件を測る。 段階の関門の前と、方針に規則を足したあとは、全件を回す。
数字の読み方の注意。 同じ構成でも、LLM の出力と TTS の長さで結果は揺れる。P2 で同じ構成を 3 回測り、揺れの幅を先に記録する。その幅より小さい差を、改善と呼ばない。

5. P1 ベンチ

エンジンより先に作る。この段階では、対話エンジンは存在しなくてよい。

作るもの

  • シナリオの型（bench/scenario.py）: 台本、流す時刻または引き金、注釈、期待する中身。
  • 入力音声の生成（bench/generate/）: 台本を TTS で読ませ、言いよどみの無音を入れ、発話の開始と終了の時刻を注釈に書く。同じ台本と種からは同じ音声ができること。
  • 再生の規則（bench/player.py）: 届いた声の断片を時刻に置く。停止が来たら、その世代を捨てる。
  • 実行（bench/run.py）: /ws につなぎ、入力を実時間の速さで送り、output.wav と実行の記録を残す。
  • 採点（bench/score/）: T1〜T5、R1 の時刻の採点。C1〜C3 の中身の採点。
  • 偽のシステム（bench/fakes/）: 無言、おしゃべり、時計じかけ。
  • 報告（bench/report.py）: 軸ごとの表、前回との差、無音の回と前提不成立の回の件数。

シナリオの量

組件数使いどころ
小各軸 10 件ほど変更のたび
全各軸 50 件ほど関門の前
本人各軸 10 件ほどP3 以降の関門で併記

台本は、最初は人が書いたものと LLM に作らせたものを混ぜる。小の組と全の組は、台本を重ねない。全の組を見ながら方針を調整しない。

P1 で決める定義

  • 出力にかける VAD の設定と、発話区間のまとめ方（短い切れ目をつなぐ長さ）。
  • 短い反応と本発話の境。仮の値は有声 1.0 秒。
  • 各軸の窓の長さ（応答を待つ秒数、割り込みと数える範囲）。
  • 採点役の LLM と、採点の指示文。

決めた定義は v4/_docs/bench-definitions.md に書き、以後は変えるたびに版を上げる。版の違う結果を比べない。

関門: 3 つの偽のシステムが、期待どおりの点になる。同じ偽のシステムを 2 回測って、時刻の指標が VAD の刻み以内で一致する。
人間がすること: 採点役は Claude の API（2026-11-10 決定）。API の鍵を用意する。合成の入力を数件聴いて、言いよどみと割り込みが不自然すぎないかを見る。

6. P2 基準線

いちばん単純な構成を通しで動かし、最初の数字を取る。賢い仕組みは入れない。

  • 通しの経路: /ws、VAD（無音 400 ms で言い終わりとする）、STT、手前の LLM、TTS、送信。
  • トレース: 入力の開始と終了、VAD の判定、STT の途中経過と確定、LLM の最初の文字と完了、TTS の最初の音と完了、送信、停止の要求と適用を、別のイベントで記録する。
  • ブラウザ: マイクと再生だけのページ。ヘッドセットで実際に話せること。
  • STT の途中経過の実測: 200〜300 ms おきの再認識で、遅れ、書き換わりの割合、LLM と同時に回したときの時間を取る。
  • 揺れの幅: 同じ構成で小の組を 3 回測り、軸ごとの幅を記録する。
  • 報告: v4/_docs/baseline.md に、全軸の数字と、遅れの内訳（どの部品に何 ms）を書く。
関門: 全軸で数字が出ている。無音の回が 0 件ではなくても、件数が報告されている。揺れの幅が分かっている。
この段階の数字は悪くてよい。目的は、どの軸がどれだけ悪いかを知り、P3 の目標を置くことである。P3 の目標の数値は、基準線の報告を見てユーザーと決める。

7. P3 指揮者とセンサー

ここが v4 の本体である。2 節の回し方で、1 つずつ足す。順番は、効果が大きく単純なものから。

順足すもの狙う軸
1tick の指揮者と世代。P2 の経路を、指揮者が働き手を起こす形に組み直す。振る舞いは変えない。R1（数字が P2 と同じであること）
2STOP。ユーザーが話し始めたら、LLM と TTS を取り消し、再生を止める。T4
3STT の途中経過と PREPARE。無音を待たずに返事を作り始める。T1 の遅れ
4MaAI vap。言い終わりの見込みで SPEAK を早め、言いよどみでは待つ。T1、T2
5相手の相づちと割り込みの区別。短い声では止まらない。T3
6MaAI bc による自分の相づち。T5
7手前の LLM の比較（E4B と 26B）。C1、C2、T1 の遅れ
  • 4 の前に、MaAI vap の当たり具合を単独で測る。合成の入力と本人の録音の両方で、言い終わりと言いよどみを見分けられる割合を出す。
  • 方針の規則は、足すたびに単体試験を書く。閾値には名前を付け、トレースに残す。
  • 規則の数が 10 を超えそうになったら止まり、整理するか学習に置き換えるかをユーザーと相談する。
関門: 間合いの軸（T1〜T4）が、P2 のあとに決めた目標に届いている。R1 は 0 件。本人の録音の組でも、同じ傾向が出ている。
人間がすること: 本人の録音の組を作る（台本を読む。30 分ほど）。節目ごとに 10 分ほど実際に話して、数字と体感が合っているかを伝える。相づちの頻度は、聴いて決める。

8. P4 裏の仕事

  • 依頼: 手前の LLM が、調べものが要ると判断したときに印を出す。指揮者が裏の仕事を起こす。
  • Web 検索: 検索と、結果を短くまとめる大きい LLM。v1 の調査の仕組み（tomoko-research-operator）の境界を読み、使える部分を持ち込む。
  • 差し込み: 結果を文脈の末尾に <info> として足す。出どころと取得した時刻を付ける。
  • 待つ間: 手前の LLM が先に短く受け、会話を続ける。結果が届いたら、切りの良いところで伝える。
  • 決定的な側の責任: 期限切れの結果を捨てる、同じ依頼を重ねない、私的な情報を検索語に入れない、失敗を知らせる。
  • 割り込みとの関係: 裏の仕事の最中でも、ユーザーは割り込める。話題が変わったら、届いた結果を言わない選択ができる。
関門: C3 で、最初の受け答えが T1 と同じ速さで出る。答えが届くまでの間に、決めた秒数を超えて黙り込まない。正答率が報告されている。T1〜T4 が P3 より悪くなっていない。
人間がすること: 検索に使う手段を決める（どの検索サービスを使うか、費用をかけるか）。検索語に入れてはいけない情報の範囲を決める。

9. P5 長時間

  • 圧縮: 約 5 分ごとに、古い部分を要約に置き換える。原本は残す。切り替えは依頼と依頼の間に行う。
  • 30 分の連続: シナリオをつなげて 30 分流し、5 分ごとに T1 の遅れと C2 の正答率を出す。
  • 資源: メモリの伸び、tick の締切超過、圧縮の瞬間の途切れを記録する。
関門: 30 分で、T1 の遅れが最初の 5 分より悪化していない（揺れの幅を超えない）。圧縮の前に話した内容を、圧縮のあとに聞かれて答えられる。

10. P6 実際に話す

  • ヘッドセットで日常的に使い、気になった場面をシナリオに足す。
  • 本人の録音の組を増やす。
  • 記憶と人格を、v1 の資産から戻す。原本と索引の区別を保つ。
  • 任意: 貯まったトレースと注釈で、方針を小さな学習モデルに置き換える実験をする。ベンチで規則の方針と比べ、良いほうを残す。
関門: ユーザーが、日常で使えると判断する。

11. P7 公開の準備

  • 既定の構成を、ライセンスの問題がない部品だけで組む。
  • リポジトリのライセンスを決める。
  • ベンチを、単独で使える形に切り出す。シナリオと生成スクリプトを同梱する。
  • 説明を書く。何ができて、何ができないか。測り方と数字。Shizuku-Duplex のような一つのモデルではないこと。
  • 別の機械で、手順どおりに動くことを確かめる。
関門: 他人の機械で、説明の手順だけで動き、ベンチの小の組が回る。

13. 止まって相談する条件

  • 段階の関門を通ったとき。報告して、承認を待つ。
  • 関門に 3 回続けて届かず、原因が分からないとき。
  • 新しいソフトを入れる、費用がかかる、外のサービスにデータを送る、のどれかが必要になったとき。
  • この文書か ARCHITECTURE.html に書いていない境界や部品が必要になったとき。
  • 2 つ以上の進め方があり、優劣が付かないとき。
  • ライセンスの条件が読み取れない部品を、既定の構成に入れたくなったとき。
  • 方針の規則が 10 を超えそうなとき。

相談するときは、状況、試したこと、分からないことを v4/MEMORY.md の「未解決の疑問」に書いてから止まる。判断を勝手に下して先へ進まない。

追記 2026-11-10（Claude Code / Fable 5.2）: P0 と P1 の結果

  • P0 は関門を通った。 ライセンスの一覧は _docs/licenses.md、持ち込む候補は _docs/carry-over.md。部品は同梱せず外部から呼ぶので、既定の構成に入れられない部品はない。使う人の側の条件は一覧に書いた。
  • 4 節の改め: .gitignore に v4/work/ は足していない。直下の work/ の行ですでに除外されている。代わりに .env を除外した。
  • 5 節の改め: 偽のシステムは 4 つにした（「礼儀正しい」を追加）。引き金に after_reply を足した。定義は _docs/bench-definitions.md（版 1）。
  • P1 の関門: 偽のシステムは期待どおりの点になった。繰り返しの一致は VAD の刻み（0.032 秒）以内。ただし、遅れの誤差は +0.022〜+0.047 秒で、刻みを最大 0.015 秒超える。この条件を改めるかは、ユーザーが決める。
  • P1 で残っているもの: 全の組（各軸 50 件）、C3 の台本（P4 で作る）、本人の録音の組（P3 で作る）、人による合成の入力の聴取。

追記 2026-11-10（2）: P1 の関門の条件を改め、P2 へ進む

  • 5 節の関門の改め（ユーザーの決定）: 「時刻の指標が VAD の刻み以内で一致」に加えて置いていた遅れの誤差の条件を、0.05 秒以内とする。P1 の関門は通った。
  • ユーザーは合成の入力を聴き、「このまま使える」と答えた。
  • P2 へ進む。手前の LLM のサーバーは、エージェントが起こす（ユーザーの承認）。

追記 2026-11-10（3）: P2 の結果

  • いちばん単純な通しの経路（VAD 400 ms → Whisper turbo → Gemma 4 E4B → Kokoro）で、小の組を 3 回測った。報告は _docs/baseline.md。
  • T1 の遅れは中央値 2.1〜2.3 秒（3 回の幅 0.13 秒）。内訳でいちばん大きいのは TTS の最初の句（0.7〜0.9 秒）。
  • 小の組では、T2・T3 の割合が 3 回で 0.2 揺れた。0.2 以内の差は判断に使わない。
  • P2 の関門（人間が基準線の報告を読み、P3 の目標の数字を決める）は、まだ通っていない。

追記 2026-11-10（4）: P2 の関門を通り、P3 の途中の結果

  • P2 の関門（ユーザーの決定）: TTS を VOICEVOX（春日部つむぎ）に替える。P3 の順番は「最初の句を短く → 頭の無音を切る → 言い終わりを MaAI に → 割り込みで止める」。STT と LLM を RTX 3060 に出す。目標の数字は決まっていない。
  • 結果は _docs/p3-results.md。T1 の遅れ中央値は 2.1〜2.3 秒 → 1.27〜1.36 秒（VOICEVOX の逐次合成を別の機械で動かし、割り込みで止める構成）。T4 は 10 件とも止まる。T5 の遮りは 42 → 0。
  • 悪化: 相づちで止まる回が 10 件中 3 件。
  • MaAI の下調べ: 合成音声では、言いよどみは分かれるが、文と文の間は分かれない。入れるかどうかは人間が決める。
  • STT を 3060 に出す構成は、3060 が応答しなくなり、測れていない。
