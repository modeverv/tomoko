## 結論

**学習なしの上書きでは、Moshi に外から与えた文を話させることはできなかった（機械的な照合で）。**
狙った文の断片（「最近読んだ…がすごく面白かったよ」「…見つけたんだ」「気をつけてね」）は声になるが、
文としては崩れる。M 案で Gemma の文面を話させるには、KAME 型の入力列を足す学習が要る見込みが高い。

## 条件

- J-Moshi-ext MLX q4、Mimi は MLX 版、text temp 0.7 / audio temp 0.8、試行ごとにモデルを作り直し（seed は試行番号で変える）。
- 入力: `say -v Kyoko` の日本語 10 文（24 kHz）。前 1 秒・後 8 秒は無音。
- 置き換える文: 各入力に対する返事として作成者が書いた 10 文（`REPLIES`。Gemma の出力ではない）。
- 照合: Moshi の出力音声を `mlx-community/whisper-large-v3-turbo`（ja）で書き起こし、狙った文との文字誤り率（CER、句読点・空白・長音記号を除く）。
  Moshi 自身の発話（上書きなし）では、書き起こしと Moshi のテキスト列の CER は中央値 約 0.3 だった。
  つまり **Moshi の音声は普段はテキスト列にほぼ従っており、Whisper の照合も目安として使える**。

## 方式と結果

| 方式 | 中身 | テキスト列に狙った文が入った | 狙った文との CER（10 文） | 崩れ方 |
|---|---|---|---|---|
| a | Moshi が語を出そうとした tick だけ置き換える（話す間合いは Moshi） | 10/10（1 文は最後の 1 token が残った） | 0.47〜0.95、中央値 約 0.8 | 断片は合う。語の長さが合わず潰れる・別の語になる。2 件で「ご視聴ありがとうございました」（Whisper の無音時の幻覚） |
| b | Moshi 自身の語を 3 token 通してから置き換える | 9/10（1 件は Moshi が 3 token 以内で話し終えた） | 0.37〜1.0、中央値 約 0.8 | a と同程度。1 件は同じ語の反復に陥った（b-04） |
| c | 発話終了直後から毎 tick 連続で置き換える | 10/10 | 0.88〜1.0 | ほぼ全滅。速すぎて声にならない |
| p | Moshi の形（語の前に EPAD、文字数に応じた PAD）で外から並べる。1 文字 1.6 / 2.2 tick | 10/10 | 中央値 約 0.85（1.6）、約 0.9（2.2） | a より良くならなかった |
| none | 上書きなし（基準） | — | （Moshi 自身のテキスト列との CER 中央値 約 0.3） | — |

起点 → 終点「入力発話の最後のサンプル → 置き換えた最初の語の tick」: a は 0〜480 ms、b は 560〜1,120 ms（Moshi 自身の 3 token の分だけ遅い）。

## 解釈（作成者の推測を含む）

- Moshi の対話モデルでは、テキスト token と第 1（意味）コードブックが同じ tick に出る。音声の中身は本体 Transformer の
  隠れ状態で大半が決まり、depformer に渡す text token だけでは引っ張りきれないと見える。
- Kyutai TTS（同じ構造で「テキストを話させる」モデル）は、テキストを音声より 16 step（1.28 秒）先に置くよう学習している（`sources.md` §8）。
  対話モデルはこの先行が 0 なので、上書きした語を本体が「準備」できていない。KAME が学習で入力列を足したのと整合する（KAME 論文はそう述べてはいない）。
- テキスト列の基準値（語の前に必ず EPAD、長い語の後に PAD、1 文字あたり 1.4〜1.9 tick）は p 方式の設計に使った。

## 残ること

- 試していないもの: 文頭を数 tick 前から先行させる（例: 1 文字ぶん先に出す）、temp を下げる、q8。どれも根本（先行 0）を変えないので優先度は低い。
